# P14 Hotel onboarding adapter boundary

**Status: design contract only.** P13 remains a review/readiness workflow; this note does not add an execution endpoint or claim that P14 is implemented. Use the existing tenant provisioning plan as the sole approval record. Do not introduce a second provisioning system.

## Authority and execution gate

The adapter may execute only a persisted plan whose current status is `APPROVED`, with successful `READY` dry-run evidence, `approvedAt` and `approvedById`, and an active persisted SUPER_ADMIN actor rechecked at execution. Keep P13's review sequence intact: `validateTenantProvisioningPlan` is mutation-free with respect to tenants and records structured checks; `markTenantProvisioningPlanReady` requires passing READY evidence; `approveTenantProvisioningPlan` approves without execution. Do not bypass review, treat `proposedCustomDomain` as an instruction, or reinterpret P13 warnings as approval.

P13 does not store an immutable approved snapshot fingerprint, and an approved plan can be returned for review. Before execution, the adapter must canonically snapshot the exact plan fields it consumes and bind the operation receipt to plan ID, approval actor/time, `validationVersion`, `updatedAt`, P13 `idempotencyKey`, and a SHA-256 fingerprint. Re-read and compare under the write transaction; reject stale, changed, returned, cancelled, failed, or already-conflicting plans. Persist an execution receipt and status/audit transition atomically with provisioning. An exact retry returns the same result; a changed actor, key, or fingerprint conflicts. The plan's unique `idempotencyKey` is not itself an execution receipt.

**Hotel scope mismatch requiring an explicit decision:** P13's `proposedOrganizationType` supports `SHOP` and `APPOINTMENT`; it has no Hotel vertical/property fields. The existing bootstrap creates `type=SHOP, vertical=HOTEL`. A P14 adapter must require a separately reviewed, explicit Hotel mapping and approved property name/slug, or reject the plan. It must never infer that every SHOP plan is a Hotel plan or silently alter an approved plan.

## Existing building blocks and transaction boundary

- P13 contract and checks: `lib/tenant-provisioning/tenant-provisioning-plan.service.ts` — `validateTenantProvisioningPlan`, `markTenantProvisioningPlanReady`, `approveTenantProvisioningPlan`, `returnTenantProvisioningPlanForReview`, `cancelTenantProvisioningPlan`, and `updateTenantProvisioningPlan`. Execution transitions to `EXECUTING`/`COMPLETED` are explicitly rejected today.
- Hotel bootstrap and invitations: `lib/organization-onboarding/service.ts` — `OrganizationOnboardingService.bootstrapHotel`, `issueInvitation`, `redeemInvitation`, and `revokeInvitation`. `bootstrapHotel` initializes an active `HOTEL_WEBSITE` capability, closed organization state, settings, one Hotel property, durable `OrganizationAcquisition.metadata` receipt (`SECURE_HOTEL_BOOTSTRAP_V1`, actor/key/fingerprint), and audit log. It does not grant `HOTEL_BOOKING`, create users, or publish a site.
- HTTP entry points: `app/api/platform/organization-onboarding/hotel/route.ts` and `/invitations/route.ts`; `lib/organization-onboarding/http.ts` derives actor from session, enforces same-origin/platform role, and validates idempotency keys.
- Existing bound invitation issuance requires an already-existing active CUSTOMER whose exact username, current email, and email verification record agree. It creates only the scoped `ADMIN`/`MANAGER` invitation; the first response reveals its one-time token, retries do not. Redemption creates/reuses organization membership without elevating global role. P13's owner name/email/phone is not a user ID or verified identity, so it cannot authorize account creation, membership, or invitation delivery.

`OrganizationOnboardingService` currently owns its own serializable transaction in a private `transaction()` wrapper, and its operations take a `PrismaClient`, not a caller transaction. Calling `bootstrapHotel()` from a future P14 transaction would nest/escape the required transaction and would not atomically commit the P13 execution receipt/status. The future adapter needs transaction-client-aware primitives (or equivalent internal refactoring) so plan reread, conflict/fingerprint checks, organization/capability/property creation, bound invitation issuance if separately approved, execution receipt, and durable audit writes share the same database transaction. Do not describe that same-transaction adapter as present. Do not emit email/SMS or other external side effects inside retryable transaction work.

## Hotel property and CMS handoff

Use the established Hotel property model and CMS, not a parallel site or provisioning path. Bootstrap property `isActive=true` has no pending state; operationally treat it as pending until owner-approved content is reviewed and an approved website revision is published. Keep `isOpen=false`; `HOTEL_BOOKING` absent; no room/rate/inventory or public booking setup is implied.

CMS entry points are `app/[locale]/dashboard/hotel-website` and its organization/property workspace. Revision lifecycle is the existing API under `app/api/organizations/[id]/hotels/[propertyId]/website/revisions`: create/edit, submit, review, preview, publish, plus publication history/revoke routes. Publication is an independent authorized editorial action, never a side effect of tenant creation. Test localized `fa`, `en`, and `ar` content and RTL/LTR rendering, including missing translations remaining empty. Verify the intended public route `https://bazarbaaz.ir/damoon-hotel` and expected `/fa` redirect only against the authorized deployment; neither is evidence of current Production behavior.

## Minimum focused Production preflight and release gates

1. Under an approved read-only target connection, verify database/branch identity and read only the minimum needed fields: whether organization slug `damoon-hotel`, intended property, and exact operator/invitee user identities already exist; active/deleted state; identity/email-verification conflicts; memberships; `HOTEL_WEBSITE`/`HOTEL_BOOKING` capability state; and any existing publication/revision state. Never guess IDs or contact details, select secrets, adopt an existing row by mutating its receipt, or turn an unverified identity into an invitee. Record unavailable or conflicting evidence as a blocker.
2. Reconcile the production migration ledger with source checksums and approved lineage, including `20260715000100_tenant_provisioning_readiness` and `20261015160000_bound_organization_invitations`. The latter has SQL-only uniqueness/check/trigger contracts. Existing lineage blockers require their own reviewed resolution. Obtain explicit migration approval; do not infer Production parity from local acceptance.
3. Require separate approval for deployment and migration, with an operator-reviewed rollback/reversal plan. Preserve organization, property, audit and content records; revoke unused bound invitations or separately authorize scoped membership deactivation. Do not delete tenant/user data or roll back unrelated ledgers.
4. After the authorized execution, verify the durable plan receipt/idempotency and audit, organization and property binding, capability state (`HOTEL_WEBSITE` active, `HOTEL_BOOKING` absent), closed booking state, and invitation binding/recipient evidence. Then use distinct authorized editorial review/publication, verify CMS access and `fa`/`en`/`ar`, and check the intended public path and unpublished/published behavior. Keep execution, migration, deployment, CMS publication and public-route evidence distinct.

Current repository evidence is local implementation/acceptance only. No Production existence check, migration, provisioning, invite delivery, CMS publication, deployment, or public-route verification is asserted by this contract.
