# Media Migration Runbook: Vercel Blob to Persistent Disk / Future S3

Status: planning only. This document does not authorize or perform a database change, media transfer, upload, deletion, deployment, or production credential access. The proposed `/disk/media` location is not implemented. Counts and byte totals remain **UNVERIFIED** until collected from an authorized, read-only Production inventory.

## Goal and constraints

Move media delivery from Vercel Blob to durable storage available to the application server, with a future S3-compatible adapter option. Preserve every existing public URL and private access rule during and after migration. Keep this as a storage-backend extension to existing abstractions; do not create a parallel media table unless the R6.2 design proves the current records cannot represent provider/key/URL compatibility safely.

The repository already has two related abstractions with different scope. `lib/storage/application-storage.ts` defines the tenant-keyed application storage boundary used by Creative Studio and AI-media imports; its `ApplicationStorageAdapter` is in `lib/storage/types.ts`, and production Vercel operations are isolated in `lib/storage/vercel-blob-storage.ts`. The broader legacy upload path uses `lib/blob-storage.ts` and `lib/media-storage.ts`, which currently call the same Vercel adapter but store filename-only keys and persist `Image.url`. Private retail receipts bypass the public-fallback wrapper and call `lib/storage/vercel-blob-storage.ts` directly. R6.2 must decide whether to unify these behind one compatible gateway or add disk/S3 implementations to both seams without breaking established data contracts. Do not route private receipts through `uploadToBlob`: it can retry a requested public upload as private, or a requested private upload as public, based on store configuration.

`lib/storage/local-test-storage.ts` is a hermetic test adapter, not a production disk implementation. It refuses production, restricts its root to the workspace, and uses test injection. Do not relax it or point it at `/disk/media`. A production disk adapter needs its own explicit configuration, readiness gate, access controls, tests, and operational contract.

## Migration design requirements for R6.2

- Extend/reuse `ApplicationStorageAdapter` only after documenting how it maps legacy image uploads, tenant AI assets and receipts. Likely needed capabilities include store, remove, verify, stream/read, and public-delivery URL resolution; public and private behavior must be explicit in types. Keep filesystem paths private to the server.
- Treat `provider + key + access + canonical/legacy URL` as an object reference. Preserve the old URL as a resolvable alias or maintain an approved mapping so embedded `Image.url`, product/gallery references, PWA manifests and published paths continue to load. Existing Blob URLs may remain live during transition. Do not mass-rewrite all DB fields to `/disk/media`.
- Disk layout proposal only: `/disk/media/<tenant-id>/<media-id>` for tenant-owned objects, with separately designed system namespace for non-tenant/public static imports. Validate tenant and media IDs against strict allowlists. Derive target paths from trusted record metadata, never request paths or untrusted filenames. Canonicalize root and parent, reject traversal and symlinks/reparse points, ensure resolved paths remain below root, and protect against TOCTOU changes as far as platform/filesystem APIs allow.
- Atomic durability proposal only: write a same-filesystem unique temp file with restrictive permissions; stream with byte limit and checksum; fsync file; atomic rename to final key without clobbering; fsync containing directory where supported; then commit/update metadata. Make retries idempotent with an operation/idempotency key and verified checksum. Document unsupported fsync semantics rather than promise durability. Validate that configured disk is actually persistent across process restart/redeploy and available to every serving replica before activation.
- Enforce MIME allowlists plus content signature, byte limits, generated immutable media IDs, content-disposition/nosniff, safe cache policy, and authenticated tenant scope. Never serve private receipts or AI-private assets from a static public directory. Public routes must check the database/alias access flag or an equivalent signed policy before bytes are served.
- Deletion should first mark a tombstone or enqueue a durable deletion intent, verify no live references remain, retain a recoverable quarantine/trash window, then remove bytes after retention. Preserve audit history. Failed compensation and orphan cleanup must be observable and idempotent. A failed DB write after file commit must leave a discoverable orphan manifest, not silently discard the only copy.
- Keep future S3 as another adapter behind the same contract, with a capability matrix for conditional put, multipart, checksum, private reads, delete/version retention and URL generation. Do not design application code around disk-only semantics that cannot be represented in S3.
- Check the object/disk inventory against quota, free-space floor, inode/file-count limits, throughput, backup, restore, replication and disaster-recovery needs. No capacity conclusion is available in this document.

## Phased execution runbook (future authorized work)

### Phase 0 — Freeze scope and evidence

Keep R6.1 documentation-only. Before R6.2 implementation, approve inventory scope, source-of-truth domains, privacy boundary, target host/storage access, retention/deletion rules, rollback window, and exact no-go gates. Capture baseline commit/schema and deployment IDs. No DB schema change is implied here.

### Phase 1 — Build inventory and reconcile

Run the read-only algorithm above on a fixed cutoff. Produce sanitized manifests partitioned by public/private class and tenant. Validate parser coverage with known code families and reviewed samples, without reading media bytes. Classify every unresolved URL/key. Stop if private/public status or tenant ownership is ambiguous.

### Phase 2 — Implement adapter and compatibility delivery

In an authorized change, extend the existing abstraction, or add the smallest justified compatible seam for legacy paths and receipts. Add disk path safety, atomic write/read/remove/verify behavior, readiness and disk-full handling, observability and a disabled-by-default provider selector. Preserve current Blob operation as rollback/source until acceptance. Keep `/uploads/[filename]` historical URL aliases working and ensure direct Blob URL consumers remain supported during migration. Keep private receipt and AI routes authenticated, tenant-scoped, non-redirecting and no-store.

### Phase 3 — Dry-run plan and manifests

Generate deterministic checkpoints containing object ID, tenant ID, source provider/key/URL alias, access, MIME, byte size, expected checksum (only if safely available through metadata or an approved source-read phase), target key, related reference families/count, and state. Never put credentials or raw personal metadata in a manifest. Dry-run must make zero writes and report collisions, unmapped references, insufficient capacity and unsupported metadata. Use a signed/checksummed manifest, immutable run ID, cursor/checkpoint and per-object status for restartability. Record source inventory cutoff and late-write strategy.

### Phase 4 — Copy in bounded batches

Only after authorization and verified disk guarantees, read each approved source object through an authenticated server-side migration tool, enforce MIME/size limits, compute SHA-256 while streaming, write atomically, fsync where supported, read back/verify checksum and access policy, then checkpoint success. Never delete source objects during copy. Do not rewrite DB references until all destinations for the approved batch are verified. Throttle to measured capacity and record retryable vs terminal failures without leaking raw payloads.

### Phase 5 — Dual-read/cutover and reference reconciliation

Use an explicit, reversible source precedence and compatibility alias map. Test old public URLs, `/uploads` aliases, product galleries, restaurant/service pages, hotel published media, tenant PWA icons, AI-media private content, and private receipts through their real application routes. For URL migration, update only enumerated live domain fields in transactions or bounded idempotent batches with tenant predicates and expected-old-value checks; retain immutable snapshots/history. Re-scan the database and resolve every live reference to verified content. Verify private routes deny anonymous, cross-tenant and public static access.

### Phase 6 — Acceptance, rollback and cleanup

Acceptance requires exact counts/bytes reconciled, zero unexplained missing live refs, checksum equality for every copied object, tenant/access checks, durable restart/redeploy and backup-restore evidence, disk capacity and monitoring thresholds, route/browser checks, and a recorded rollback rehearsal. Keep Blob copies and aliases through the approved rollback interval. Roll back by switching reads/writes to the known-good source and restoring DB references from the manifest with expected-old-value guards; do not delete copied files or source objects as a rollback shortcut. Source deletion is a separate, later, explicitly authorized operation after retention, backup verification, and a second complete reference scan.
