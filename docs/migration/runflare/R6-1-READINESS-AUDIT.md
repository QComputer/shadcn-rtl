# R6.1 Runflare readiness audit

**Audit type:** documentation-only, read-only source and configuration review. No provider mutation, database write, deployment, DNS/environment change, or source implementation change was performed. Environment values and private configuration files were not read. This is not a live acceptance result.

## Decision

**BLOCKED — not ready for production cutover.** The owner has identified a Runflare Node 24 target and PostgreSQL 17.4 service, but the repository still selects the Neon Prisma adapter at runtime, production media defaults to Vercel Blob, rate limiting is process-local, and Runflare proxy/cache/custom-domain behavior has not been demonstrated. The proposed `/disk/media` storage root is not implemented. Required scheduled work, if any, remains subject to the the scheduler inventory in `R6-1-READINESS-AUDIT.md`.

## Critical blockers

1. **Database adapter and connection contract:** target is PostgreSQL 17.4 but runtime hard-selects `PrismaNeon`; provider-specific pooled/direct endpoints, TLS and least-privilege role behavior are not yet confirmed here.
2. **Durable media:** production default is Vercel Blob. `/disk/media` is only a proposal; `MEDIA_STORAGE_ROOT` is not implemented. Choose and validate durable storage before accepting uploads or media writes.
3. **Runflare execution proof:** Node 24 build/start, reverse proxy, health checks, graceful shutdown, body limits, cache behavior and custom-domain request flow are not verified on a live Runflare service.
4. **Scheduled work, if required:** no cron schedule is checked into deployment config. First confirm which source jobs require periodic triggers; provide a secured, observable scheduler contract only for those jobs.
5. **Shared state under scaling:** rate limiter is in-memory; cache sharing is unknown. Do not scale horizontally until shared behavior is implemented/verified or single-instance operation is explicitly accepted.
6. **Vercel coupling:** Blob storage and Vercel Domain API/DNS automation do not become Runflare features by copying environment variables. Disable or replace each path and verify any retained external Vercel dependency.

## Disk, cost and capacity decision

No disk write, restart, redeployment, backup creation or restore was performed. Mount visibility, filesystem/UID, quotas/free bytes/inodes, single-writer versus shared replica access, locking, retention and restore guarantees remain UNVERIFIED. Official RunFlare documentation describes disk-backup creation/list/download/restore controls; it does not establish this service's backup schedule, RPO/RTO, consistency or replica-sharing contract. See the media runbook's physical tests and acceptance checklist. ([RunFlare backups](https://docs.runflare.com/general/backup-management/))

Only the app resource figures above were observed; database resources, persistent volume quota, backup capacity, egress allowance, build workspace limits and actual plan pricing remain UNVERIFIED. Required inputs are the allocated DB/disk quotas, backup policy, resource/traffic tariffs and current approved budget. Do not extrapolate prices from another provider. R6.2 must measure peak Node build/start/steady RSS and CPU, DB pool saturation, R3 500-row transaction duration, R5 aggregates/exports, upload throughput and image cache growth. Reserve separate space for media, atomic temporary files, cache and backup; do not put the only backup on the same disk. Use measured concurrency and target `max_connections` to set Prisma pool bounds.
