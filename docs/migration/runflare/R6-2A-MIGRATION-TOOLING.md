## Media plan

Run `node scripts/migration/runflare/plan.mjs --dry-run --kind media --input <sanitized-reference-and-object-metadata-json>`. This CLI consumes operator-prepared JSON; it is not a database exporter or Blob API client. Reference items may use `key`, `storageKey`, `url`, `path`, or `filename`; object metadata may use `key`, `pathname`, `url`, or `filename`. Include only safe identifiers, tenant IDs, reference family, public/private classification, byte counts, and SHA-256 values when already known. Do not include credentials, raw DB rows, customer fields, or signed URLs. URL query strings are discarded and `/uploads/` and `public/` aliases are normalized as relative keys.

Input-generator and coverage contract: prepare database references from every inventoried field family, not only `Image` rows or string columns. R6.1 confirms 188 `Image` rows (76 `/uploads` aliases and 112 tenant-relative public paths), while explicitly leaving arrays/other provider references, private retail receipts, and AI storage separate or unresolved. The sanitized generator must therefore report per-family source field/table coverage, reference occurrences, unique normalized keys, null/unowned references, and excluded/unreadable fields; it must fail the completeness claim when any relevant family was not enumerated. At minimum track `Image.url` legacy `/uploads/<filename>` and tenant-relative keys; `creative-studio` tenant assets; `retail-payment` private receipt keys; and AI-media storage references as a separate family whose concrete source fields must be enumerated before claiming coverage. Include `family` on every record. Do not invent DB or provider access in this planner; parent/operator work must supply the separately authorized sanitized metadata exports.

The planner sorts entries and emits a manifest digest. It joins normalized DB references to supplied Blob metadata and reports planned object count/bytes, adapter-compatible target key, tenant, access class, reference count/families, source bytes, expected bytes/checksum, and blockers. Legacy bare filenames map to `tenants/<organizationId>/uploads/<filename>`; known tenant-relative keys preserve their remaining path below that uploads prefix. Existing accepted `creative-studio`, `tenants`, and `retail-payment` namespaces are retained when their organization segment matches the owner. Unknown nested source-key families fail closed as `unsupported-source-key-family`; they are never flattened to a basename. Target-key collisions are blocked. Backslashes and percent escapes are rejected, including percent-encoded traversal. Missing ownership, invalid/traversal paths, cross-tenant ownership, public/private ambiguity, conflicting aliases, duplicate Blob keys, missing object metadata, unreferenced objects, and known size/checksum mismatches are blocked. Every unblocked entry is labeled `metadata-planned` with `verifiedContent: false`: it is not evidence that media bytes were downloaded or hash-verified. The planner performs no download, copy, delete, or DB reference update. A metadata-only plan cannot prove object contents or source completeness.

## Validation and limits

### RunFlare frozen-lockfile build guard

`prebuild` calls `scripts/build/runflare-lockfile.mjs`; enforcement is opt-in with `RUNFLARE_ENFORCE_LOCKFILE=1` and is bypassed on Vercel. With the flag unset, existing local and Vercel build behavior is unchanged. Under RunFlare, pnpm 10.15.0 is accepted without recursion. An npm-invoked build requires Node 24 and an actual `npm-cli.js`; it runs `npm exec --yes --package=pnpm@10.15.0 -- pnpm install --frozen-lockfile --ignore-scripts` with `CI=true` before the existing build script. Other package managers and unsupported runtime details fail closed. This guard runs after the hosting preset's initial install phase; it makes the final prebuild dependency tree follow the committed pnpm lockfile. It does not establish a build speed or memory improvement.

Run the focused unit suite with `node --test tests/unit/runflare-migration-tooling.test.mjs`. It covers source/target identity mismatch, ledger baseline drift, incomplete target and extension proof, `pg_session_jwt` portability gating, preservation of all nine Neon Auth table counts, no-execute behavior, tenant/access collisions, traversal rejection, alias normalization, checksum metadata, and deterministic output. These are pure planner checks; they are not PostgreSQL CLI, provider, backup, archive, catalog dependency, restore, or media-transfer evidence. Until root SQL-catalog review supplies verified extension dependencies and target capability, keep the planner blocked or use the target-supported `preserve-native` strategy.
