**Status: planning only; production deployment is blocked.** This plan is pinned to source baseline `368e545e40cca95ddd9749d42c560d7444b1daa5`. Root-audit facts: Runflare project `36927`, app/service `85798`, Node `24.22.1`, npm `11.6.0`, 2 GB RAM, 1 GHz CPU and 2 GB base storage. These are read-only console observations recorded by the root agent. Build, start, health, upload, database connection and migration have not been demonstrated on Runflare. The project is connected to `QComputer/shadcn-rtl`, branch `main`, with Auto Pull already enabled. Preserve that setting during R6.1. It means a future main merge may deploy to both providers before an operator is ready. The owner separately authorized publishing this R6.1 documentation branch with exactly one `vercel.json` branch-only deployment suppression. It does not change main, RunFlare or any other branch.

## Deployment mechanism and package boundary

The installed Runflare CLI is `v1.2.2`; only version/help were inspected. Its `deploy -y` route uses the cached project and is prohibited for this service. If a separately authorized manual deployment uses CLI, interactively select project `36927` and service `85798`, verify both identifiers in the confirmation context, then inspect upload root and exclusions. Never substitute `-y`, cached-project deploy, cached logs/events or cached lifecycle commands for explicit project selection. Official reference: [Runflare CLI commands](https://runflare.com/docs/work-with-cli/cli-commands/). CLI `status` output reports local file changes and is not application-health evidence; use service events/logs plus real HTTPS probes.

For Git or any future explicitly selected CLI upload, package only the intended source and lockfile. Exclude `.git`, `.env*`, private config, credentials, tokens, database dumps/archives/backups, `node_modules`, build output and local evidence. Review the artifact file list and secret scan before upload. Never package `bazar-baz-current.dump` or another database dump. Store secrets only in the approved Runflare secret store; use the reviewed subset from `ENVIRONMENT-MAPPING.md`. Do not copy Vercel credentials unless a separately approved external integration requires them.

## Build and runtime contract

The pinned source lock resolves Next `16.2.7`, Prisma `6.19.3` and React `19.2.3`; `package.json` declares `pnpm@10.15.0`, lockfile v9. The observed console exposes npm `11.6.0`, and source has no Node `engines` field. Scripts define `build` as `npx prisma generate && next build` and `start` as `next start`. Before launch, choose a deterministic package-manager and build contract that honors `pnpm-lock.yaml`; prove a frozen-lockfile install and production build on the exact Node 24 target. Do not silently install from package ranges with npm or replace/regenerate the lockfile. Then prove process start, restart, HTTPS health, graceful shutdown, memory use and request limits on the actual service. Establish where build occurs and whether its 2 GB storage is ephemeral or persistent before relying on it for media.

PostgreSQL needs a code change before runtime use. `lib/db-runtime.ts` currently hard-selects `PrismaNeon`; the installed `@prisma/adapter-pg` is not wired into runtime. The existing owner-reported target is PostgreSQL `17.4`, database `databasewhy_db`, owner `postgres`, internal service `database-giu-service`; the endpoint, TLS and grants need current confirmation. Existing target emptiness is unknown. Use only this existing database, and restore only if it is proved empty and the data owner approves. Never create another database or service. If the target contains any object or emptiness cannot be proved, stop. Implement explicit PostgreSQL runtime use through PrismaPg, retain separate runtime and direct maintenance/migration URLs, and validate pool bounds plus transactions, row locks, `SKIP LOCKED`, advisory locks and isolation levels used by commerce/job code. Never run migrations on application startup. Follow `DATABASE-MIGRATION-RUNBOOK.md` for separately authorized restore/migration operations.

Media is also a hard prerequisite. Existing storage abstractions are present, but production defaults to Vercel Blob and `MEDIA_STORAGE_ROOT` has no consumer. There is no production `/disk/media` adapter. Do not advertise the proposal as configured. R6.2 should implement the proposed persistent-disk adapter, retain a future S3-compatible seam, and prove its durability across restart/redeploy, independent backups, permissions and every serving replica. A metadata scan finding zero literal `blob.vercel-storage.com` URLs does not prove no stored objects exist; reconcile all aliases and object metadata. Preserve tenant paths, historical URL aliases and private receipt handling. Use `MEDIA-MIGRATION-RUNBOOK.md` for inventory and transfer gates.

## Runtime acceptance gates

1. Prove real Runflare TLS proxy behavior: health endpoint, forwarded Host/proto, custom-domain rewrites, auth callback/CSRF/logout, request/body limits, streaming, timeouts and graceful termination. `proxy.ts` and Next 16 routing are core behavior.
2. Approve platform origin, TLS/DNS owner and supported custom-domain flows. Keep `lib/vercel-domain-automation.ts` disabled on Runflare; it calls Vercel APIs and encodes Vercel DNS targets.
3. Begin with one instance unless shared cache/limiting is implemented and verified. `lib/rate-limit.ts` uses a process-local `Map`; cross-instance `revalidatePath`/`revalidateTag` behavior is unproven. Do not scale horizontally until shared behavior or an explicitly accepted single-instance contract is proven.
4. Keep SMS, web-push, AI-provider and real-send integrations disabled/dry-run until individually approved. Use the exact internal payment-expiration/verification and notification paths inventoried in `R6-1-READINESS-AUDIT.md`; establish actual source schedules and one active caller before transferring any job.
5. After restore, test representative tenant reads/writes, cross-tenant and anonymous denial, auth sessions, static assets, public media aliases and private receipt access. No production traffic until these pass.

## Stop and rollback conditions

Stop if deployment identity/branch is ambiguous, package contains secrets/dumps, build/start/health evidence is missing, PostgreSQL identity or adapter semantics differ, startup migrations are proposed, media durability/access is unresolved, tenant acceptance fails or resource limits are exceeded. Keep source Vercel serving until the separately authorized R6.4 write-freeze and final snapshot/media reconciliation. DNS reversal alone is insufficient after Runflare accepts writes because database and media state can diverge. Rollback then requires a write freeze and reconciliation/replay decision for all Runflare writes; never leave both systems writable.
