## Fulfillment and payment configuration

- Pickup and delivery are enabled; configured delivery fee is **50,000 Toman**, requiring merchant confirmation before real use.
- The stored pickup address is a short placeholder. Organization phone/email are absent, and no business hours are configured. Coordinates alone do not establish a usable pickup location.
- Delivery coverage, restrictions, handling expectations, return and size-exchange policies require merchant input. The default preparation duration is not a verified shipping promise.
- Current cash policy is **COUNTER, before order acceptance**. This is not an automatic cash-on-delivery promise. Confirm actual receipt before marking collected. Courier/pickup collection requires a deliberately configured compatible policy.
- Bank transfer is disabled. The existing bank-transfer flow, if later configured, uses customer evidence and merchant review; it is not automatic bank settlement.
- No Aka Shoes integration record exists. No live gateway was enabled. iNoti readiness additionally requires an active connected tenant integration, allowed merchant profile, HTTPS endpoint and secret credentials, callback origin, tenant policy, runtime/live-verification approval gates and a production hash pepper.
- Retail totals use Toman; iNoti converts to rial by **×10**. Legacy organization currency metadata says IRR and must not be used to apply an additional conversion to Retail prices.
- iNoti settlement validates provider read-back, exact amount/session/reference/account identifiers and idempotency. Its public callback is not a signed webhook. A sandbox/provider-contract exercise and explicit live activation approval remain required.
- Retail refunds are not implemented as a reconciled financial workflow. P1.3 rejects the generic REFUNDED transition instead of recording a false refund or restoring stock without financial reconciliation.

## Merchant operations and access

One active Aka Shoes ADMIN membership was verified for `ahmad`; there is no active MANAGER membership currently. Existing Retail merchant APIs permit active ADMIN/MANAGER memberships with SHOP capability, scoped to the active organization. STAFF order-reading permission does not grant Retail catalog or cash-collection authority.

Three existing shared orders remain PENDING, including two Retail QA cash orders and one legacy order. No order was paid, canceled, deleted or reprocessed during this audit. Existing stock movements are preserved.

P1.3 fixes:

1. Public order organization-wide access now requires an active staff role, active user and active organization; own-customer, guest-session, scoped bearer-token and platform-admin paths remain supported.
2. New USSD events no longer persist the raw order tracking bearer token. Historical event retention needs separately approved review; this patch does not rewrite history.
3. Same-status order retries no longer duplicate history/notifications. Paid Retail refunds remain blocked pending a real refund workflow.
4. Merchant order details expose purchased names, SKU and options from immutable snapshots, recent status history and the existing authorized cash-collection action with an explicit confirmation. Cash collection updates the existing payment ledger, never a second payment system.

6. ذخیره کنید، صفحه را دوباره باز کنید و نتیجه را در پیش‌نمایش و صفحه عمومی بررسی کنید. کالای بدون گونه قابل خرید نمی‌شود. انتشار صرفاً به معنی آماده‌بودن اطلاعات برای فروش نیست.
7. نشانی تحویل حضوری، تلفن، ساعات کار، محدوده ارسال، هزینه واقعی، شرایط تعویض سایز و مرجوعی را پیش از فروش واقعی تأیید و در تنظیمات پشتیبانی‌شده تکمیل کنید.
