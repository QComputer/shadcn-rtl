# P1.4 — Merchant account and session security

Baseline: accepted main `5723418b3bbbcdb86209cf8a3e69c07ec0ef28c1`. Preview-only release; no Production deployment or shared database migration is authorized by this change.

## Root cause and implementation

NextAuth uses encrypted 30-day JWT sessions. Previously neither its JWT callback nor the protected API guard compared a session with the credential that originally authenticated it. Changing the bcrypt hash left older authenticated devices valid.

New JWTs contain a server-keyed HMAC of the user ID and bcrypt hash. The password and bcrypt hash are never included in the JWT or public session response. The existing NextAuth JWT callback checks the current active user's credential on every session read, including direct `auth()` consumers; mismatched credentials return no session. Client session updates cannot replace the binding. Live global roles are also re-read. Credentials login binds the hash actually verified, preventing a login racing a reset from acquiring the replacement credential's binding. Existing Google sign-in maps the already permitted local account before applying the same binding.

Password changes require the current password, a same-origin request, existing authenticated-user rate limits and a replacement password of at least 8 characters within bcrypt's 72-byte limit. A compare-and-set update prevents two concurrent changes from both succeeding. Updating the credential, recording the revocation event and invalidating outstanding recovery links are transactional. Audit failure rolls back a credential change. **All previous sessions are invalidated, including the current session, across all organizations.** The UI signs out and explains that a fresh login is required. Organization-admin reset uses the same invalidation/audit mechanism; its authority remains tenant-scoped and does not grant global roles.

Unchanged legacy JWTs are retained. Before adding a binding to a legacy token, the server checks durable password-change/admin-reset audit markers against its original issue time. An older raw token cannot refresh into the new credential version after a reset. Existing shared accounts are not rotated or revoked merely to demonstrate this behavior. Session checks fail closed on database errors. Requests already authorized before a password change are not canceled mid-flight.

No schema migration, new authentication system, new session table or new shared secret is required. The existing NextAuth secret keys the binding. Existing cookies and 30-day expiry remain in place. Each session read incurs an active-user/credential query; a legacy session additionally checks credential audit history until upgraded.

## Recovery availability

**Self-service delivery is deliberately CONFIGURATION_REQUIRED.** The current application has no completed email delivery implementation and no verified phone identity suitable for account recovery. Existing SMS order notifications do not establish verified recovery ownership. No provider was invented or activated, and no notifications were sent.

`/{locale}/forgot-password` now provides a Persian configuration-required explanation and a safe return to login. `/api/auth/recovery` reports availability without looking up an account. While disabled, request/consume endpoints return the same configuration-required response for every account; no usable recovery token is issued. This is an intentional availability limit, not a claim that recovery delivery works.

The server-only recovery core reuses `PasswordReset`, `EmailVerification` and `AuditLog`:

- Cryptographically random 256-bit recovery credentials; only a domain-separated SHA-256 digest is stored.
- Exact verified-email ownership, a 15-minute expiry, single use, invalidation of older outstanding links, and account-scoped issuance limits.
- Database-backed attempt limits serialized with advisory locks: 5 requests or 10 consume attempts per IP/15 minutes; account issuance capped at 3/15 minutes even across IPs. Endpoint process-local limits add an inexpensive first layer.
- Row locking and atomic token claiming protect concurrent recovery. A successful recovery changes the credential, invalidates all older sessions and recovery links, and records a secret-free audit event in one transaction.
- The delivery adapter is server-owned and unconfigured in the deployed application. Tests inject an in-memory verified channel; it cannot be enabled by a client or by an unreviewed environment flag.

Before activating recovery, a separate reviewed integration must connect an existing verified channel, use a trusted configured origin and a non-leaking link transport, and validate provider behavior and asynchronous acknowledgement timing. The core's test adapter is not a Production email provider. No new SMS/email service or live notification is part of P1.4.

## Authorization and audit

Browser/API tests use synthetic accounts: SUPER_ADMIN, scoped ADMIN and scoped MANAGER can access Retail merchant context; STAFF, CUSTOMER and anonymous users cannot. Own account settings remain available to authenticated customers. Credential reset requires organization ADMIN or actual platform SUPER_ADMIN authority; MANAGER/ordinary membership cannot reset another account. ADMIN cannot reset another ADMIN or a platform administrator, grant platform authority or cross tenant boundaries. These accepted boundaries remain unchanged.

Security audit records contain event reasons and `allPreviousSessionsRevoked`, never passwords, password hashes, OTPs, recovery credentials, cookies or binding values. Wrong-password change attempts and stale-session rejection are recorded without credential data. Repeated stale-session audit writes are sampled per application instance; revocation itself is checked on every request and is not sampled or cached. Auth.js debug logging is disabled.

## راهنمای کاربر

1. تنظیمات حساب ← «امنیت» را باز کنید. رمز فعلی، رمز جدید یکتا و تکرار آن را وارد کنید.
2. پس از ذخیره، تمام نشست‌های حساب در همه دستگاه‌ها و سازمان‌ها پایان می‌یابند؛ با رمز جدید دوباره وارد شوید. سبد خرید و سفارش‌های قبلی حذف نمی‌شوند.
3. مدیر سازمان برای بازنشانی حساب غیرمدیر از بخش اعضای سازمان استفاده می‌کند. این تغییر نیز جهانی است؛ رمز یا کد امنیتی را در پیام یا گزارش منتشر نکنید.
4. «فراموشی رمز عبور» فعلاً وضعیت نیازمند پیکربندی را نشان می‌دهد. هیچ کد یا پیوندی ارسال نمی‌شود؛ برای بررسی هویت از مسیر پشتیبانی معتبر سازمان اقدام کنید. به درخواست ارسال رمز یا کد در پیام پاسخ ندهید.
5. پس از فعال‌سازی مجاز کانال بازیابی، پیوندها ۱۵ دقیقه اعتبار و فقط یک بار استفاده خواهند داشت. پس از انقضا باید درخواست جدید ثبت شود؛ بازیابی موفق همه نشست‌های قبلی را پایان می‌دهد.
